## 0. 先纠正一个前提（本文最重要的一条）

你原话是"1688 采集、闲鱼上架的时候采用 ai-goofish-monitor 来避免闲鱼风控"。读完 298 个文件的实现，实际情况是：

| 你的期望 | 事实 | 证据 |
|---|---|---|
| 用它防闲鱼上架风控 | **它是纯只读项目，零写操作**。全文只有 `page.goto` 搜索页/详情页 + `evaluate(scrollTo)`，没有任何发布、发消息、下单接口 | `src/scraper.py:654`(search)、`:982`(detail)、`:394-398`(personal)；grep `idleitem.publish` / `mtop.*\|send\|create\|order` 在 `src/` 与 `chrome-extension/` **零命中** |
| 用它做 1688 采集 | **完全没有 1688 逻辑**，域名硬绑 goofish/taobao | grep `1688\|alibaba` 全仓零命中；`config.py:20-21`、`scraper.py:395,640,654` |
| 抄它的反检测技术 | **技术通道不同，抄不了**。它用 Playwright 开真实 Chrome，**mtop 请求是页面自己发的，它只是 `page.on("response")` 被动捕获结果**——签名、token、Cookie 全部由真实浏览器上下文产生 | `scraper.py:355-390`（被动监听）、`:552,569,591`（launch/new_context/storage_state） |

**这条必须写进认知**：它最大的安全优势恰恰是"我们放弃的那件事"——我们走 mtop HTTP 直连、自己算签名，等于没有浏览器行为轨迹。所以下面 §1 的纪律性策略对我们**比对它更重要**，而 §2 那些浏览器技巧对我们**完全无意义**。

一句话：**能迁的是"操作纪律"（熔断、重试分类、节奏、并发、幂等），不能迁的是"反检测技术"（JS 注入、启动参数、指纹覆写）。**

## 1. 直接可迁移（8 条，带具体参数）

### 1.1 熔断器 `failure_guard.py` —— 最值得整块照搬

| 参数 | 值 | 位置 |
|---|---|---|

| 熔断暂停时长 | **24 小时**（`TASK_FAILURE_PAUSE_SECONDS`，默认 `24*60*60`） | `:172-176` |
| 暂停下限 | **60 秒**（防配置成 0 导致风暴） | `:173` |
| 状态存储 | `logs/task-failure-guard.json`，`fcntl` 文件锁互斥 | `:164-168`、`:90-110` |
| 写入方式 | 原子写 + `fsync` | `:136-143` |
| 状态文件损坏 | **改名保留现场**再继续，不崩溃 | `:127-133` |
| 暂停期通知 | **每天最多 1 次**（`last_notified_date`） | `:263-281` |
| 时区 | `Asia/Shanghai` 显式指定 | `:177` |
| 恢复路径（三条，无需人工点开关） | ① Cookie 文件 **mtime 变大** → 自动重置计数并放行 ② 暂停到期 ③ 一次 `record_success` | `:79-87`、`:240-261`、`:324-327`、`:204-218` |
| 确定性错误（缺代理/缺登录态） | 阈值降为 **1**，立即熔断，不浪费重试 | `scraper.py:121-135` |
| 双重检查 | 调度进程启动前 + 子进程内各查一次 | `process_service.py:140-146`、`scraper.py:1198-1223` |

**迁移到 `xianyu-core` 的方式**：

- 我们现在只有令牌桶限速（`protocol.md §1.4` 写操作 1 次/分钟）+ RGV587 熔断 10 分钟。**两层要叠加而非替换**：10 分钟是"接口级短期节流"，24 小时是"账号级止损"。
- 按操作域拆 **3 个独立 guard key**：`publish` / `reply` / `delivery`，比它的 `task_name` 更细——发布挂了不该把自动发货一起停掉。
- 解锁信号照抄 mtime 思路，但换成我们的存储：**该账号 `AccountAuth.last_login_at` 变新 → 自动解除熔断**（用户重新扫码即恢复，不需要额外按钮）。~~文档字面原为 Cookie 行的 `updated_at`~~：已否决（2026-09-19 决定）——`auth/refresher.py` 保活每 30 分钟滚动回写 `encrypted_cookie`，会连带刷新 `updated_at`，24h 熔断将在半小时内被误解除；`last_login_at` 仅在扫码确认路径（`account_service.py`）更新，才是"重新扫码"的真信号。
- 熔断状态必须在 Dashboard 可见（见 §4 R-9）。

### 1.2 失败分类决定是否重试 —— 直接回答"避免 LLM 操作时报错"

它的语义（`scraper.py:1269-1283`）：

| 错误类型 | 它的处理 | 迁移到我们 |
|---|---|---|
| `LoginRequiredError`（URL 被重定向到 `passport.goofish.com` / `mini_login`，`scraper.py:78-82`） | **break，绝不重试** | 标记该账号"待重新扫码"，停止其全部写操作，报人工 |
| `RiskControlError`（滑块中间件、`FAIL_SYS_USER_VALIDATE`） | **break，绝不重试**，注释明说"不是简单轮换能解决的" | 立即熔断 + **禁止 LLM 自行重试**（这是最关键一条） |
| 网络/超时/解析失败 | 换账号或换 IP 重试，`attempt_limit = max(账号retry, 代理retry)`，默认 2、下限 1 | 可重试，但**只在同一账号内**换凭证重试 |
| `TOKEN/SESSION 过期`（可自动恢复） | — | 走三轨保活刷新（`protocol.md §2.3`），刷新失败升级为登录态失效 |

**这条为什么对我们比对它更要紧**：它失败了可以换个账号换个 IP 再来，而 LLM 拿到一个"失败"结果时的本能反应就是**重试**——风控类错误的重试恰恰是加重风险的举动。所以必须在工具层（不是提示词层）把"不可重试"编码成硬返回，让模型拿不到重试的余地。

注意：它**爬虫侧没有指数退避**（固定 `delay=5, retries=3`，`utils.py:18-48`、`search_pagination.py:17-18`）。别以为它有多先进的退避算法，这块我们反而可以做得更好——写操作用指数退避 + 抖动。

### 1.3 节奏参数基线（均匀随机，非高斯）

`utils.py:61-65` 的 `random_sleep` 是 `random.uniform` 均匀分布。它实测在用的数值：

| 动作 | 间隔 | 位置 |
|---|---|---|
| 每个商品详情处理完 | **5–10s** | `scraper.py:1113` |
| 翻页之间 | **10–15s** | `scraper.py:1144` |
| 进详情页前 / 关闭详情页后 | 2–4s / 2–4s | `:975`、`:1137` |
| 打开首页后的前置伪装浏览 | 1–2s ×2 + 随机滚动 200–700px | `:645-649` |
| 搜索提交后 | 1–3s | `:684` |
| 各类筛选操作（区域/包邮/价格/排序） | 1–2.5s | `:746-902` |
| 命中 `FAIL_SYS_USER_VALIDATE` 后 | `random.randint(3, 60)` 秒休眠再抛 | `:1002` |

**迁移**：`10–15s` / `5–10s` 这两档是"同一目标站连续两次导航"的实测安全基线，可作为我们 mtop 写操作间隔的**下限参照**。我们现有的 `publisher.upload_images` 逐张 0.3–0.8s 抖动（`publisher.py:121`）是"同一动作的批量子步骤"，量级不同，两者不冲突。**"命中风控先随机休眠几十秒再放弃"这一条值得抄**——它避免了抛错瞬间被上层循环立刻重试打回去。

### 1.4 保守并发 + 同账号互斥

- AI 分析信号量默认 **2**（`scraper.py:237-240`）、图片下载 **3**（`ai_handler.py:60-63`）——它的默认值非常保守，值得学；
- 一任务一进程一浏览器，重复启动由 `is_running` 挡住（`process_service.py:111-117,133-138`）；
- **它的短板必须避免**：`spider_v2.py:192` 用 `gather` 同时跑所有任务，**跨任务无全局限流**。

**迁移**：我们已有 `asyncio.Semaphore(1)` 同账号串行（`protocol.md §1.4`），但要在**定时任务层再补一条全局约束**：同一账号同一时刻只能存在一个"发布类"任务实例（`auto_listing` 与手动放行、MCP `publish_goods_now` 三者互斥）。否则批量放行 + 定时轮询会并发打到同一个号。

### 1.5 凭证/代理拉黑 + TTL —— 附带一个必须修的缺陷

`rotation.py:37-43,46-51,31-35`：失败即 `mark_bad` 拉黑，TTL 默认 **300s**，选取是 `random.choice` 而非轮询。

**它的缺陷**：账号池与代理池**各自独立随机**（`rotation.py:31-35`），**没有做账号↔IP 绑定**。同一账号上一分钟在上海 IP、下一分钟在广州 IP，是最典型的风控触发特征。

**迁移规则（硬性）**：若我们引入代理，**必须固定"一个账号一个出口"**，禁止两个池独立随机。这条对我们比对它更严重——我们本来就少了浏览器行为轨迹这层掩护。

### 1.6 读侧去重 → 发布幂等键

它的幂等做法：`processed_links` 从历史结果加载（`scraper.py:471-477`）、`get_link_unique_key` 取 `&` 前的稳定段（`utils.py:117-119`）、命中即跳过（`:964-969`）、结果黑名单关键词支持 `re:` 前缀（`result_blacklist_service.py:9-40`）。

**迁移**：把"链接稳定段"换成 **1688 `offer_id` 作为发布唯一键** → 正好落在设计文档 §9-1 要加的 `Goods.source_offer_id` 唯一索引上。一个改动同时解决"报错 bug"和"防重复上架"两件事。再加一条它的 `Goods.external_goods_id + status==1` 已在售防重（`api/routes/goods.py:134-135`）作为第二道。

### 1.7 规则引擎优先、LLM 兜底 —— 少让模型进操作循环

它有 `decision_mode ∈ {ai, keyword}`（`scraper.py:457-460`）+ `keyword_rule_engine.py`，能用规则判的绝不调模型。

**这条本身就是风控措施**：LLM 每多进一次操作循环，就多一次"它可能决定重试/改参数/换个说法再发"的机会。我们的 `price_and_write_copy` 应当同样：`clean_title` + `markup_price` 能覆盖的场景不必问模型，只在需要市场判断时叫 LLM——这与设计文档 §7.1 的三级降级链是同一思路的延伸。

> **2026-09-20 修正注（别把这条读成"文案可以不走模型"）**：「规则优先」管的是**判断**（价格倍率、状态流转这类可算的东西），**不适用于成品文案**。`clean_title(源标题)` 是喂给模型的打底输入，不是可以替代模型产出的文案成品——把去噪后的 1688 营销标题当成品写进 `decision`，等于把上游话术原样搬去闲鱼，且那类标题动辄 >30 字、带「超级/爆款」，落库即撞 `title_too_long`（该拦截项又属"改文案救不了"一类，重写循环不会去救它），件件卡死在放行闸门前。现在文案这一环**刻意没有降级链**：模型不可用就留空 + `copy_source="none"`，宁可行置灰也不要假成功（详见主设计 §7.4、接口文档 v1.8）。

### 1.8 参数取"真实快照"，不要硬编码猜

它最聪明的一条：不维护静态 UA 池，而是用 `chrome-extension/background.js:246-289` 从**真实登录浏览器**里导出 cookies、`navigator/screen/intl`、经 `webRequest` 拦截的真实请求头（allowList `:166-184`），再用 `scraper.py:279-326` 覆写回 Playwright context、`:584-586` 回放真实请求头（`_build_extra_headers:329-338` 显式排除 `cookie`/`content-length` 防冲突）。

**迁移**：我们 mtop 请求里的 UA、`x-features`、`appVersion`、`x-sufei-token` 这类常量，应当从**自己账号的真实抓包**里取并配置化，而不是照抄网传值或让 LLM 编。同一程序内**不同用途刻意用不同 UA** 也值得注意（它图片下载用桌面 Firefox UA，`config.py:51-57`）。

## 3. 它完全没有、不要指望的东西

1. **发布/写操作前的任何保护**：没有提交前确认、没有防重复提交、没有写操作频控（因为它压根不写）。→ 我们的 `confirm_token` + 状态机闸门（设计文档 §8.1）是**自研的，无参考**，属于本项目风险最高的一块，M5 必须重点实测。
2. **商品文案 / 定价 / 客服话术提示词**：`prompts/` 里只有选品判定，**一条都没有**。具体是 `base_prompt.txt`（EagleEye-V6.4 外壳，强制单 JSON 输出 `is_recommended/reason/risk_tags/criteria_analysis`）、`macbook_criteria.txt`（品类判定标准）、`prompt_utils.py:10-36` 的 **META_PROMPT（用 LLM 生成新品类的 criteria 文本）**。注意它的 `risk_tags` 是**识别卖家风险**（区分"高级玩家 vs 贩子"），不是反检测。
3. **自动过滑块/验证码**：三类检测全都在发现后**直接放弃不重试**（`scraper.py:687-732,995-1011,1273-1277`）。
4. **自动重登/保活心跳**：无。Cookie 失效只能人工换 state 文件，靠 mtime 变化自动解锁。→ 我们已有三轨保活（`protocol.md §2.3`），**这块我们比它强**。
5. **1688 采集**：零。

唯一值得从它"选品提示词"里借的结构，是 `macbook_criteria.txt` 那四条原则的写法——**画像优先 / 一票否决项 / 图文冲突以图为准 / 信息缺失标 `NEEDS_MANUAL_CHECK` 而不是直接否决**。最后一条对我们尤其适用：定价证据不足时应转 `pricing:"manual"` 交人工，而不是让模型硬猜。

## 4. 落到本项目：LLM 操作风控守则（10 条硬约束）

**实现位置一律在代码层，不依赖提示词自觉。** 提示词可以被越狱、可以幻觉，代码层闸门不行。

| # | 规则 | 阈值/触发 | 实现位置 |
|---|---|---|---|
| R-1 | 大模型不得直接调用平台写接口 | 只允许产 `decision` | `mcp/` 工具层不暴露任何裸 mtop 调用 |
| R-2 | 写操作熔断 | 连续 3 次失败 → 暂停 24h；**2026-09-20 修正：`kind=network`（连接被断 / 超时 / 网关回 HTML = 请求没送达闲鱼）不计数**，否则三次本地抖动就换来 24h 止损，方向错了；**同日补：`kind=local_throttle`（自己令牌桶 1 次/分钟没排到号）同样不计数**，它是本项目排队、请求根本没出门，真机上两次排队就被记成 2/3 额度 | 新建 `core/failure_guard.py`，参照 §1.1；豁免判定在 `listing/publisher.py:publish_goods` 的失败分支 |
| R-3 | 三个操作域独立熔断 | `publish` / `reply` / `delivery` 各自计数 | guard key 分域 |
| R-4 | 风控类错误**禁止重试** | 命中滑块 / `FAIL_SYS_USER_VALIDATE` / RGV587 → 立即抛终态错误，工具返回 `retryable:false` | 错误分类对齐 `protocol.md §1.3` |
| R-5 | 登录态失效**禁止重试** | 重定向到 passport / 缺 `unb` → 标记账号待扫码并停止其写操作；**2026-09-20 补：「失效」不能只看 `hasLogin.do` 的文案**——真机上同一份 Cookie 一分钟前刚发布成功、下一分钟就被它报「登录态已失效」。置 0 前必须再过一次只读 mtop 复核（`loginuser.get`），只有它也回 `FAIL_SYS_SESSION_EXPIRED` 才算失效；被标 0 的号按 15min 低频复核，复核通过自动回 1 并重挂会话池 | 同上；Skill 必须显式报告，不得静默 |
| R-6 | 熔断前随机静默 | 抛错前 `random.randint(30, 300)` 秒 | 防上层循环立刻打回（借 §1.3 `:1002`） |
| R-7 | 同账号写操作互斥 | 一账号同时只有一个发布类任务（定时 / 前端放行 / MCP 三入口互斥） | 补 §1.4 那条全局约束 |
| R-8 | 发布幂等 | 唯一键 `source_offer_id` + 在售防重 `external_goods_id` | 对齐 §9-1 迁移 `0005` |
| R-9 | 熔断状态可观测 | 流程面板与 Dashboard 显示 guard 状态、剩余时间、解锁方式 | 前端新增（见设计文档 §8.4） |
| R-10 | LLM 无权自行放宽任何上述限制 | 不向模型暴露任何 `force` / `skip_risk` 参数（`propose_listing` 的 `force` 只用于覆盖**本地未确认**的 decision，与平台写操作无关） | MCP 工具入参白名单 |
