# xianyu-core 后端接口文档（REST + WebSocket）

> 版本：v1.13（2026-09-20）
> 说明：本文档梳理 **自建后端** 对外全部接口，供前端薄面板与脚本/curl 共用（同一套 API，零重复开发）。
> 闲鱼私有协议（mtop 签名 / WS LWP 帧）不在本文范围，见 `protocol.md`。
> 交互式文档：启动后端后访问 `http://localhost:8000/docs`（Swagger）。
> 验证状态（2026-09-20）：后端 **353 单测全绿**；前端 **vite build 通过**，14 个 View 已过逐页烟测，采集页另做过真号端到端。**成品文案只出自模型**（v1.8）：`copy_source` 只能是 `llm` / `human` / `none`（`none` = 那一轮模型没产出来，附 `copy_error`），不再回落 1688 源标题。**发布链路真号首跑（v1.9）**：`imageInfos` 传成 URL 字符串数组会被闲鱼读成 `FAIL_SYS_SERVICE_INNER_FAULT::服务内部故障`（看着像平台挂了，实则我们 body 不对，见 `protocol.md §3.4`）；该步失败照样计入 `publish` 域写失败额度，3 次 → 24h 熔断（手动发布 429、`auto_listing` 跳过），解锁只有到期或重新扫码（`last_login_at` 变新），**禁止手删状态文件绕开**，所以首次跑这条链先只放行 1 件。**上架报错的读法（v1.10）**：传输层异常（`ConnectError` / 超时 / 响应体非 JSON）此前会冒成裸 **500 Internal Server Error**，现统一在请求层折算成 `kind=network` → **502 + 带异常类型的 detail**，并且**不占 `publish` 域写失败止损额度**、**不改 `pool_status`**（件留在 `MAPPED`，下轮自动重试）；只读调用自动补发 1 次，**写调用绝不自动重发**（断连 ≠ 闲鱼没收到）。**自己令牌桶排队（v1.12）**：「写操作限流：Ns 后重试」是本项目 1 次/分钟的排队、请求根本没出门，此前折成 `unknown` 会被记成一次平台写失败（真机两次排队＝2/3 熔断额度），现在单独折算成 `kind=local_throttle` → **429**，与 network 同口径：不占止损额度、不改 `pool_status`。扫码登录已实测可用。**新加的 `/api/collect/run`、`/api/collect/search-1688`、`/api/collect/schedule` 在旧容器里是 404**——backend 镜像没挂源码也没开 `--reload`，要 `docker compose build backend && up -d --force-recreate backend`。**前端反代 `/api/` 的读超时已配到 900s**（v1.7：此前不写＝默认 60s，配模型后 `/api/collect/run` 必然 504，而那一轮其实跑完了）。**不带服务名的 `docker compose restart` 是个坑**：四容器同时重启，backend 会先撞一次连不上 MySQL（镜像 CMD 有重试环，能自愈），且 nginx 启动时把 `backend` 解析成**旧容器 IP** 缓存下来 → 之后 `/api/` 全部 502（直连 8000 却正常）。要么先 `restart backend` 再 `restart frontend`，要么事后单独重启 frontend。**「每次切 tab 闲鱼 Cookie 都在校验」已修（v1.13）**：切 tab 本身不发任何平台请求（每个 View `onMounted` 只是重拉 `/api/accounts` 把已有的徽章重显一遍），真凶是保活调度器在**扫码后 1–2 分钟**跑的首次 `hasLogin` 把刚验证可用的号标成 0，且旧实现里 0 是单向门（`_tick` 不再选它、启动恢复也不选它）⇒ 见下方 §2 账号表 `cookie_status` 那行与 `protocol.md §2.3`。

## 0.1 通用约定

| 项 | 约定 |
|----|------|
| Base URL | `/api`（nginx 反代 `location /api/` → backend:8000） |
| WebSocket | `/ws/messages`（**不带** `/api` 前缀，nginx 单独反代升级头） |
| 数据格式 | 请求/响应均为 JSON；列表接口直接返回数组（无分页包装） |
| 错误格式 | FastAPI `HTTPException`：`{"detail": "<中文可读原因>"}`，状态码 400/404/500/502 |
| 金额 | 一律「分」（`price_cent`），前端展示时 `/100` |
| 时间 | `message_time` 为毫秒时间戳（闲鱼侧全是 ms）；`last_login_at`/`occurred_at` 为 ISO datetime；DB 时间戳统一 Python 本地时钟 |
| 外部 ID | 闲鱼侧重外部 ID（unb/商品/订单）一律字符串，不转数字 |
| 鉴权 | **JWT Bearer**（v1.3 补记：`/api/auth/*` 早已实现但本文漏记）。除 `POST /auth/register`、`POST /auth/login`、`GET /health` 与 `GET /api/collect/offers/{b}/{o}/images/{name}`（取舍见设计文档 D-2026-09-19-9）外全部需带 `Authorization: Bearer <token>`；数据范围按登录用户收敛（非 admin 只见自己账号的商品/订单/消息/账号/熔断） |

## 1.5 系统登录（auth，v1.3 补记）✅
`app/api/routes/auth.py`，prefix `/api/auth`。这是"面板多用户"那一层，与 §2 的**闲鱼扫码登录**是两回事，别混。

| 接口 | 说明 |
|------|------|
| `POST /api/auth/register` | 建面板用户 `{username, password, remark?}` → `{"user": {...}}`，固定 `role:"user"`；用户名重复 409。密码走 `users/security.py` 哈希，明文不落库不落日志 |
| `POST /api/auth/login` | → `{access_token, token_type:"bearer", user}`；前端存 localStorage（`api/index.js:getToken`），后续请求带 Bearer。口令错/用户不存在 401，`status!=1` 403「账号已停用」 |
| `GET /api/auth/me` | 当前登录用户 `{"user": {...}}`（需 token） |
| `POST /api/auth/logout` | 无状态 JWT：前端删 token 即登出，后端只回 `{"ok": true}`，**不吊销 token** |

> ⚠️ 一期口径：`register` 是**公开端点**且前端登录页有「注册新账号」入口（代码注释即"注册策略默认开放；正式运营可改白名单"）。数据范围按 `user_id` 收敛，所以新用户进来看不见别人的商品，但**能自建账号并让定时任务用他的 Cookie 干活**。挂公网前必须先关注册或加邀请码——与 §11 的"上服务器前补鉴权"同批处理。

### `GET /api/accounts` — 账号列表（脱敏）
只暴露昵称/状态，**不含任何登录态**（Cookie 由后端会话池管理，前端与 Agent 都不碰）。

响应字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 内部账号 ID（后续接口的 account_id） |
| nickname | string\|null | 昵称 |
| external_uid | string | unb（闲鱼用户 ID） |
| status | int | 0 停用 / 1 启用 |
| cookie_status | int | 0 待校验 / 1 正常 / 2 过期（RGV587 风控不误标，只入滑块流程）。**v1.13 起 0 不再是单向门**：置 0 前要先过一次只读 mtop 复核（`hasLogin` 的文案单独不算数），已标 0 的号每 15min 复核一次，通过就自动回 1 并把会话重挂回会话池（详见 `protocol.md §2.3`） |
| fish_shop_user | bool | 是否鱼小铺账号（发布接口两套） |
| last_login_at | datetime\|null | 最近登录时间 |

### `POST /api/accounts/qr-login` — 生成扫码登录二维码
响应：`{"session_id": "<uuid>", "qr_image": "data:image/png;base64,..."}`（qr_image 为 data URI，直接放 `<img src>`）。
失败：502 `{"detail": "生成登录二维码失败: <异常类型>: <原因>"}`。
这一段是**串行打三个外网接口**（h5api 取 `_m_h5_tk` → `mini_login.htm` 提 `viewData` → `generate.do` 出码），
每步 `timeout=20s`；采集那一轮在跑时会把容器网络/CPU 占住，此处最容易先读到超时——
2026-09-20 就撞过一次，当时 httpx 的 `ReadTimeout` 的 `str()` 是空串，前端只显示到冒号，
现已在 detail 里带上异常类型。

### `GET /api/accounts/qr-login/{session_id}` — 轮询扫码状态
前端 1s 一次。状态机：`new`（等待扫码）→ `scaned`（已扫待手机确认）→ `confirmed`（成功）｜`expired`｜`cancelled`｜`verification_required`｜`error`。

`confirmed` 时后端自动：Cookie AES-GCM 加密入库 + 会话池注册 + 拉起该账号 WS 监听，并在响应里附带：

```json
{ "status": "confirmed", "account_id": 1, "nickname": "小号A" }
```

### `GET /api/goods?category=A|B` — 商品列表 ✅
可选 `category` 过滤：`A` 虚拟（手动上架+卡密自动发货）/ `B` 1688 采集（人工履约）。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 内部商品 ID |
| external_goods_id | string\|null | 闲鱼商品 ID（未上架为空） |
| category | "A"/"B" | 品类 |
| source | string | manual / 1688 / csv |
| title | string | 标题 |
| price_cent | int | 售价（分） |
| status | int | 0 下架 / 1 在售 / 2 已售 |
| pool_status | string\|null | 商品池状态机（品类 B）：SOURCED→DECIDED→MAPPED→PUSHED/FAILED（`DECIDED` 为 v1.3 新增，见 §3.5） |

### `POST /api/goods` — 手动登记商品 ✅（阶段 4-5）
品类 A：闲鱼 App 手动上架后登记（绑 external_goods_id，自动发货按它匹配）；品类 B：商品池入库。Body：

| 字段 | 必填 | 说明 |
|------|------|------|
| account_id | ✅ | 归属账号 |
| title | ✅ | ≤128 字 |
| category | "A" | A 虚拟 / B 采集 |
| price_cent | ✅ | 售价（分），>0 |
| description | | 描述（上架时用） |
| image_urls | | 图片 URL 列表（上架需 ≥1 张首图） |
| external_goods_id | | 选填：已在闲鱼手动上架则填，重复登记 400 |
| source | manual | manual / csv / 1688 |

响应 `{"id": 1, "title": "...", "status": 1}`；有 external_goods_id 即视为在售（status=1、pool_status=PUSHED），否则待上架（status=0）。

### `POST /api/goods/import-csv` — CSV 批量导入品类 B 商品池 ✅
粘贴文本导入（列 `title,price(元),image_urls(分号分隔)[,description,source_offer_id]`；首行可为表头；空行/`#` 注释忽略；同账号同标题去重）。导入即转换（标题去噪 + 加价）入池 pool_status=MAPPED。

Body：`{"account_id": 必填, "csv_text": ≤200KB, "markup_rate": 默认 1.3 (0.5-3.0)}`。
响应：`{"added": 新增数, "skipped": 去重跳过数}`。

### `POST /api/goods/collect-1688` — 1688 详情页批量采集 ✅（v1.3 补记，本文原列 §11"暂缓"已过时）
Body：`{"account_id": 必填, "offer_ids": [≤100 个] }`。非登录 httpx 直连详情页解析（`parse_offer`），逐件落 `data/collect/<batch>/offers/<id>/`（`product.json` collect 段 + 图片）并写 Goods 行。
**入池只到 `pool_status=SOURCED`**（v0.6 防线修正：不再直写 `MAPPED`，见设计文档 §8.1）。同批去重跳过已在池的 offer。
响应：`{"batch_id": "...", "added": n, "skipped": n, "failed": n}`。
本接口**不触碰闲鱼平台**（只出 1688 的 GET）。定价/文案另走 §3.5 的 `…/decide`。⚠️ 字段映射未经真实页面验证，见 §11。

### `POST /api/goods/{goods_id}/publish` — 上架 ✅（阶段 4-5）
四步发布链路（传图→类目→地址→提交，`listing/publisher.py`；写操作限流 1 次/分钟，耗时约 30s+）。
成功：external_goods_id 回填 + status=1 + pool_status=PUSHED + 发布快照落库（`goods_edit_snapshot`，快照回放式重发的根基）。
失败：502（闲鱼接口错误，pool_status=FAILED）或 400（本地校验如无图片，不动 pool_status）；409 = 账号未登录；**429 = 我们自己没让请求出门**——两种：`publish` 域止损熔断中（`WriteGuardPaused`，到期或重新扫码才解），或写操作令牌桶没排到号（v1.12，detail 形如「写操作限流：30s 后重试」，稍后重发即可）。两者都不动 pool_status。
**v1.10 修正（裸 500 → 可读 502）**：网络/传输层异常（`ConnectError`、超时、响应体不是 JSON）此前从 `MtopClient` 一路冒到路由外，用户看到的就是一句「上架失败：500 Internal Server Error」＋后端一屏栈。现在请求层把它折算成 `kind=network`：回 **502 + detail 带异常类型**（如 `mtop … 网络异常（ConnectError，请求未送达闲鱼）`），并且 ① **不占写失败止损额度**（三次本地抖动不该换 24h 熔断，手册 §4 R-2），② **不改 `pool_status`**（件留 `MAPPED`，`auto_listing` 下轮自然重试，不用人工重点一次），③ 只读调用在客户端自动补发 1 次、**写调用（第 4 步 publish）绝不自动重发**——断连不等于闲鱼没收到，重发就是重复发布。图片上传与源图下载两跳同口径。
**v1.11 修正（第 3 步「账号无默认收货地址」＝我们读错了层级）**：`poi.get` 真机取证（`backend/scripts/spike_poi_get.py`，只读一发）显示 **`data` 顶层只有 `selectedPoi`，`commonAddresses` 这个键根本不存在**，且字段名是 `poi` / `latitude`+`longitude`（无 `gps`）、`divisionId` 是 int——旧实现去 `commonAddresses[]` 里逐条找 `selectedPoi` ⇒ 恒空 ⇒ 把"账号有地址"误报成没地址并**硬失败**（还占一次写失败额度）。现在：顶层取 `selectedPoi`、兜底 `commonAddresses[0]`，`gps` 拼成 `经度,纬度`，`poi→poiName`；**取不到地址时不再抛错**，改成 warning + 空 `itemAddrDTO` 继续发（goofish-cli 同口径：无地址传 `{}` 也能发布，商品只是不显示所在地）。入参带不带经纬度返回一致，故仍传 `{}`。真机形状已脱敏进 `tests/fixtures/xianyu/poi_get.json` 并锁进单测（形状细节见 `protocol.md §3.5`）。
**v1.12 修正（「写操作限流」不该烧止损额度）**：令牌桶（写操作 1 次/分钟）拒绝时抛的曾是 `kind=unknown`，`publish_goods` 照记一次写失败——真机上 `auto_listing` 把 8/9 两件连着排队两次，就变成 **2/3 次熔断额度**，第三次直接把 `publish` 域锁 24h，看起来像"发布链路又坏了"实则我们自己卡自己。现在独立成 `kind=local_throttle`：路由回 **429**（区别于熔断的到期语义）、不改 `pool_status`、不记额度，`auto_listing` 只留一行 warning 不再铺栈。细节见 `protocol.md §1.3/§1.4`。
**v1.3 追加**：`source=1688 且 pool_status ∈ {SOURCED, DECIDED}` → 400「该采集件尚未放行，不能上架」，并指引去「采集工作区」（§8.1 防线，见设计文档）。
**v1.9 修正（类目推荐请求体形状）**：链路第 2 步 `imageInfos` 原样传的是 **URL 字符串数组**，闲鱼侧不报参数错而是回 `FAIL_SYS_SERVICE_INNER_FAULT::服务内部故障`；现改为**图对象数组**（与发布体 `imageInfoDOList` 同构，复用 `ImageInfoDO`），并把"无图"从原来要打两次平台请求才 `ValueError`，改成进链路前先本地拒发（400）。形状与故障码的对照写进 `protocol.md §3.4`。
⚠️ **放行 ≠ 一次性动作**：`batch-approve` 把件推到 `MAPPED` 后，`auto_listing`（600s 一轮、单轮 ≤5 件）会自动尝试发布，失败只是"下轮重试"——**发布链路的任何请求体缺陷都会以每 10 分钟一次的节奏累计写失败，连续 3 次即触发 24h 熔断**（手册 §4 R-2）。首次真机跑这条链时先只放行 1 件。

### `POST /api/goods/batch-approve` — 采集件批量放行 ✅（v1.3）
`DECIDED → MAPPED` 的**唯一人工闸门**；闸门逻辑在 `app/collectors/pool_flow.py:approve_offers`（REST 与日后 MCP 工具 6 共用），本端点只做 HTTP 壳 + 用户数据范围校验。
Body：`{"goods_ids": [1,2] (1–5 个，超出 422), "confirm": true}`；`confirm != true` → 400。
逐件校验：`pool_status=DECIDED` / `product.json` 有 `decision` / `pricing != "manual"` / `decision.risk_scan.passed` / 有标题 / 本地已有图片 / 未在售 / 未重复放行。**任一件不合格 → 整批拒绝**，`detail` 逐件列 `#id 标题：原因（命中项以 `[code] field：term` 形式给出）`。
通过：回写 `title/description/price_cent`（`decision.orig_price_cent` 划线价与 `confirmed_by`（当前登录用户名）/`confirmed_at` 记入 `Goods.raw_payload`），`pool_status=MAPPED`。
响应：`{"approved": [1], "applied": 1}`（整批要么全放行、要么整批 400，故无 rejected 字段）。

### `PATCH /api/goods/{goods_id}` — 采集件人工改写 ✅（v1.3，缺口⑨）
`app/collectors/pool_flow.py:edit_offer` 的 HTTP 壳。**全仓库唯一的 Goods 改写入口**（其余只有 `POST /api/goods` 登记新行）。
Body：`{"title"?: ≤128 字, "desc"?: ≤4000 字, "price_cent"?: int ≥1}`，三项全不传 → 400。价格单位是**分**（不是元，别把 19.9 当 19.9 传）。
行为：把改动写进工作区 `product.json` 的 **decision 段**（不是只改 Goods 行——放行时 `approve_offers` 用 decision 抄 Goods，只改行等于白改），随后 `run_risk_scan` 就地重扫并把结论回传；填过价则 `decision.pricing` 置 `human`（否则 `manual` 的闸门永远拦着）。v1.8 同一条口径用于文案：**改过 `title` 或 `desc` 就把 `decision.copy_source` 置 `human` 并清 `copy_error`**，否则"文案未产出"这条新报因会把人工补好的件一直误拦。`SOURCED` 会被顺带推进到 `DECIDED`。同时镜像回 Goods 的 `title/description/price_cent`。
拒绝（400，走 `ApprovalError`）：非 `source=1688` 的件 / 已在售（`external_goods_id` 或 `PUSHED`）/ 无 `local_path` / **decision 段为空**（得先 `…/decide`）。product.json 缺失 → 404。
响应：`{"goods_id", "batch_id", "offer_id", "pool_status", "pricing", "price_cent", "risk_scan"}`。
⚠️ 后续对同一件跑「重跑定价」（`…/decide` 带 `force`）会**整体覆盖 decision**，人工改写随之丢失（有意不加"保护位"：force 的语义就是重出）。前端改写入口仍未接，当前只有本接口（curl）走得到。

### `POST /api/collect/run` — 一句话/关键词/offer_ids → 待确认清单 ✅

进 `collectors/pipeline.run_collect_pipeline()`，五节点代码控环（⓪ Cookie 前置 → ① 意图 →
② 检索循环（`MAX_SEARCH_ROUNDS=2`，常量，**不进配置**）→ ③ 详情页采集 → ④ 逐件定价文案+风险扫描 → ⑤ 硬停）。

- Body = **`CollectRunRequest`，与 `scheduled_task.config_json` 同一个形状**（N5 要求，参数层不允许分叉）：
  `{account_id, instruction?: ≤500 字, keyword?: ≤60 字, offer_ids?: ≤50, preference?: ≤200 字, alibaba_account_id?, max_items?: 1..50}`；
  三个来源优先级 `offer_ids > keyword > instruction`，给前两个就不花 LLM 调用；全空 → 400；
- **响应 `status` 是业务结论不是 HTTP 码**（都 200，前端按状态分别渲染，别当 5xx 处理）：
  `ok` / `needs_clarification`（缺槽位追问，不猜不跑）/ `no_source_account`（开浏览器之前就拒，不扣配额）/ `search_blocked`；
- `ok` 时附 `{batch_id, plan, searched:{rounds:[…]}, collected:{added,skipped,failed,blocked,aborted,not_attempted}, decided:[{offer_id,goods_id,stage,price_cent,title,pricing,confidence,risk_passed,risk_blockers,needs_human,error}], elapsed_ms}`；
- 4xx 只用于"调用方真的错了"：入参非法 / 账号不存在 404 / 越权 403。
- ⚠️ **这是同步长请求**：一次检索 + N 件详情页（每件 1–3s 随机延迟）+ 每件 2 次 LLM 调用。
  实测 2 件 4.2s（无 key 走规则定价）；**配上模型后 4 件就要 60s+**（2026-09-20 实测），别在前端把 `max_items` 调大。
- **504 ≠ 没跑成**：反代到点断流时，后台那一轮仍会跑完并落清单（那次 4 件全部进了 `DECIDED`）。
  前端 nginx 的 `location /api/` 原先不写 `proxy_read_timeout`，等于默认 60s，现已配到 900s；
  仍看到 504 时**先去「采集工作区」刷待确认清单**再判断成败。
- **手动入口不吃检索配额**（N7 只挂定时路径，见下）；LLM 没配 key 时 ④ 退化到 `fallback-rule`
  定价 + 源标题照抄，"标题 >30 字"这类拦截项只能人工改写。

真号实测：勾 2 件 → `新增 2 / 去重 0 / 失败 0 / 风控 0`，两件到 `DECIDED`，均被 `title_too_long` 拦成 `needs_human`。

## 8. WebSocket `/ws/messages` — 实时事件推送 ✅

订阅后端事件总线，前端拿规范化字段（**剥掉 rawPayload**）。

- 连接：`ws(s)://{host}/ws/messages`（注意：**不带 /api 前缀**；vite/nginx 均按 `/ws/` 反代并带升级头）；
- 心跳：服务端每 30s 推 `{"type": "heartbeat"}`，前端忽略即可；
- 断线：前端自行重连（骨架版总线无 unsubscribe，重连会累积空 handler，只空转）。

推送消息格式：

```json
{
  "type": "message_received | order_paid | order_created | cookie_expired",
  "account_id": 1,
  "occurred_at": "2026-09-15T10:00:00",
  "payload": { }
}
```

| type | 含义 | payload 关键字段 |
|------|------|-----------------|
| message_received | 新消息（含文本/图片） | senderUserId / senderUserName / contentType / msgContent / xyGoodsId 等 |
| order_paid | 买家已付款（触发品类 A 自动发货） | orderId / orderKey / xyGoodsId / buyerUserId / buyerName |
| order_created | 新订单（品类 B 人工履约通知） | orderId / orderKey / xyGoodsId / buyerUserId / buyerName / goodsTitle |
| cookie_expired | 登录态失效（需重新扫码） | — |

## 10. 调度 worker（非接口，main.py lifespan 启动）

`scheduled_task` 表 DB 租约（lease 三件套）抢单，多 worker 互斥；间隔由 `TASK_INTERVALS` 常量表决定（cron_expression 保留给以后接 croniter）。启动时 `ensure_default_tasks` 缺则补种默认任务行。

| 任务类型 | 间隔 | 做什么 |
|---------|------|--------|
| order_sync | 600s | 遍历会话池存活账号，sold.get 分页拉单补齐 TradeOrder（§5）；全部账号失败才记任务失败 |
| delivery_recovery | 600s | heal_stuck_deliveries：中间态超时（默认 30min）转 unknown，不回滚卡密 |
| auto_listing | 600s | 只吃 `MAPPED` 的行（= 人工放行过的）→ 上架。**这条就是"采集绝不写 MAPPED"那道防线存在的原因**（主设计 §8.1）：若采集直接写 `MAPPED`，这个任务会无人值守地把没被人看过的文案发出去 |
| **collect_1688**（v1.5） | 1800s | 到点把 `scheduled_task.config_json`（**与 `POST /api/collect/run` 同一个 `CollectRunRequest` 形状**）原样喂给 `run_collect_pipeline`，`trigger=scheduled`，终点仍是 `DECIDED`。补种行 `enabled=0`；唯一挂 `SearchQuota`（每货源账号每小时 6 次浏览器）的路径；配置缺失/非法只记日志不抛，开跑了没产出清单才抛 |

> Cookie 三轨保活**不在本表也不占 `scheduled_task` 行**：由 `auth.refresher` 的常驻循环独立负责（见 `task_runner.py` 模块 docstring）。
