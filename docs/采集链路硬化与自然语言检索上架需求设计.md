1. 本轮**推翻两条既有决策**：M3 的落地形态由「Qoder Skill + REST」（主设计 D-2026-09-19-12）改为**后端硬编码 pipeline service**；「关键词采集一期不做」（§9-5 / D-2026-09-19-11）改为**本期就做**。

5. **人工放行闸门一道都不放**：`DECIDED → MAPPED → PUSH` 仍是两道人工确认；新入口只负责把清单更早、更完整地端出来。

## 3. 架构：五节点 + 代码控环

```
run_collect_pipeline(db, *, account_id, instruction=None, keyword=None,
                     offer_ids=None, preference=None, alibaba_account_id=None,
                     max_items=None, trigger="nl", workspace=None,
                     search_quota=None) -> dict
    # 两个入口：POST /api/collect/run（trigger=nl|manual，不传配额）
    #           collect_1688_task（trigger=scheduled，传 search_quota）——参数同一个模型
    # 返回 status：ok / needs_clarification / no_source_account / search_blocked
    # —— 业务结论走 status，不走 HTTP 错误码（前端按 status 渲染追问）

⓪ 前置       pick_usable_alibaba_account() → 无可用登录态则整条链路直接返回（N8）
① 意图解析   parse_intent(instruction) → CollectPlan
             LLM 不可用 → 规则兜底（正则捞 offer_id / 价格数字），标 intent_source="rule"
             给了 keyword / offer_ids → intent_source="explicit"，不花这次 LLM
② 货源定位   plan.offer_ids 非空 → 直接用（保留人工给 ID 的通道）
             否则 for round in range(MAX_SEARCH_ROUNDS=2):   # 常量，非配置项
                 search_quota.acquire(货源账号) 拿不到名额 → 收手（N7，只挂定时路径）
                 search_offers(keyword) → 去重累加
                 命中数 ≥ plan.quantity → break
                 不足 → chat_json 判「换什么词/是否收手」→ 更新 keyword 或 break
③ 采集       executor.collect_by_offer_ids(...)          ← 存量
④ 逐件决策   decide_offer(batch, offer, preference) × N   ← 存量；逐件记账，单件失败不中断
             stage=blocked 的占位件直接 skipped，不进定价（否则给幽灵商品写出 decision）
⑤ 【停】     返回待确认清单（DECIDED 件 + 风险明细 + 定价模式）
             ★ 不 approve、不 publish —— 代码层无任何调用入口
```

**三条铁律**（沿用主设计 §4，本新增两条）：

1. 触达闲鱼平台的写出口只有 `listing/publisher.py`。`run_collect_pipeline` 全程不 import 它。
2. **闸门落代码，不落提示词**（主设计 D-2026-09-19-8）。控环的 `MAX_SEARCH_ROUNDS`、`max_items`、配额检查全部是 Python 常量或 DB 配置，模型无法越。
3. **模型不得选择要执行的动作**。LLM 的输出只能是"下一个关键词是什么 / 这批里哪几件更像目标"这类**数据**，不能是"调哪个工具"。
4. `cookie_status != 1` → 在 `launch()` 之前返回，不启动浏览器、不耗配额。
5. 一次进程内**同时只允许一个检索浏览器**（信号量），与 `auto_listing`/`order_sync` 并存时不吃爆内存。

### 4.6 定时接线（S3）的三条判断

1. **参数从哪来**：`scheduled_task.config_json`（`models/task.py:17` 起就有的 JSON 列，此前无人用）。

2. **抛错的口径**：配置缺失/非法只记日志**不抛**（"还没配"和"配了但跑炸了"混在一个计数里，

## 6. 风险与前置

1. **货源账号登录态会周期性不顶用**（主设计 D-2026-09-19-10 实测过"当天采得动、过几小时整批壳"）。措辞按 S4 实测降级：同一份 Cookie 在 22:02 整批 blocked、次日 01:16 又全绿，**说明有一部分是动态风控、会自己恢复**，不是硬过期。操作口径不变但判据改严：**验收前先确认库里 `cookie_status=1` 且不是刚整批 blocked 过**；真 blocked 时先隔一会儿重试同一件，**连续**几次仍壳才让用户重扫码。另注意所有 `data/collect/` 时间戳是 UTC（+8 才是本地）。
2. **搜索页比详情页更敏感**。缓解：≤20 条、一次只开一个浏览器、随机延迟、连续 blocked 即中止（沿用 `MAX_CONSECUTIVE_BLOCKED=3`）。定时路径另有每小时配额（N7）。
3. **无人值守串跑的成本前置**。定时一次 = N 次 LLM 调用发生在人看到清单之前。缓解：`max_items` 硬上限 + 逐件记账 + 批次 aborted 上报。
4. **改后端要重建镜像**：backend 容器没挂源码也没开 `--reload`，`docker compose cp` 进去的 `.py` 不重启不生效，表现为路由 404（不是 405/422）。但 `docker compose exec backend python -c/-m <script>` 是**新进程**，cp 完立即生效——浏览器冒烟这类无需路由的验证走这条路最快。
5. **浏览器二进制只在容器里齐**（2026-09-19 实测）：镜像 `playwright install --with-deps chromium` 装了 `chromium-1243` **和** `chromium_headless_shell-1243`；宿主原生 `.venv`（playwright 1.63）只有 `chromium-1243`，缺 headless shell。因为 `launch(headless=True)` 在 1.50+ 走的是 headless shell，**本机原生跑扫码登录（`alibaba_login.py:113`）与检索都会炸在 "Executable doesn't exist"**。
   排障口径：涉及浏览器的验证一律进容器跑，别在本机 venv。
   修法二选一，**不要为了绕过去给 launch 加 `channel="chromium"`**——那会让本机跑的二进制和线上不同，正是本项目栽过的"本地绿、线上空转"：① 本机 `playwright install chromium`（约百 MB，补齐即与容器一致）；② 什么都不改，验证只在容器做。
6. 本项目仅自有小号实测；批量铺货违反闲鱼用户协议，不做真实放量。
