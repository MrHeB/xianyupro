# 1688 采集 + 定时上架闲鱼 —— 调研与实现方案

> 版本：v0.1（草稿）
> 日期：2026-09
> 目的：为「1688 商品 → 定时自动上架闲鱼」补缺口。盘点参考项目里可复用的**采集**与**定时铺货**实现，落到我们的 `xianyu-core`（FastAPI 自建管线）。
> 边界：本文只做只读源码调研 + 落地方案，**不含对真实闲鱼/1688 账号的任何实发验证**；`ItemPublisher` 发布链路仍未小号实测。

---

## 0. 结论速览（TMDR）

1. **没有现成的「1688→闲鱼」完整闭环项目**。参考里最接近的是 **pds-tool**（1688 采集+转换+定时铺货，但目标平台无闲鱼、无签名的闲鱼封装）。
2. **采集**：pds-tool 提供了可直接移植的两条路——官方 API（`alibaba.icbu.product.search/get`，MD5 签名）与页面解析兜底（httpx + 正则提取内嵌 JSON）。这跟我们在 `流程方案.md` §1.2 的决策一致（非登录采集）。
3. **定时铺货**：pds-tool 用 **APScheduler `IntervalTrigger 60s` 扫表 + `cron_expression` 存 DB + `CronTrigger.from_crontab` 算 `next_run_at`** 的模式，恰好避开了 `apscheduler` 需要为每个任务注册 job 的多租户痛点——**其设计可直接照抄给我们**（其现有 4.5 的 `task_runner` 就是这一思路的 DB 租约版）。
4. **闲鱼侧发布**：不归采集文档管，`ItemPublisher`（`xianyu-core/backend/app/listing/publisher.py`）已按 goofish-cli 四步链路实现，待小号实测。
5. **待验证项**：pds-tool 的 `parser.py` 存在 `url` 未定义变量 bug；1688 搜索页反爬未知；官方 API 需 ISV 资质。见 §3.3。

## 2. 采集：1688 非登录 + 官方 API 双路

### 2.1 官方 API（pds-tool `backend/app/sourcing/alibaba.py`）

- 网关：`https://gw.open.1688.com/openapi`，路径 `/param2/{version}/{namespace}/{method}/`
- 签名（`alibaba.py:54-59`）：**参数升序拼接 → 首尾拼 App Secret → MD5 大写**：

```python
def _sign(self, params):
    items = sorted((k, str(v)) for k, v in params.items() if v is not None and v != "")
    joined = "".join(f"{k}{v}" for k, v in items)
    raw = self.app_secret + joined + self.app_secret
    return hashlib.md5(raw.encode("utf-8")).hexdigest().upper()
```

- 接口（`alibaba.py:92-124`）：
  - 搜索 `alibaba.icbu.product.search`（namespace `com.alibaba.product`，v1.0.0）参数：`keywords/categoryId/beginPage/pageSize/sortType(va综合·wp价格升·wd价格降·rz销量)/priceStart/priceEnd`
  - 详情 `alibaba.icbu.product.get` 参数：`productID`
- 返回归一化（`_normalize_search` / `_normalize_detail`）统一字段：`offer_id / title / price / stock / image_urls(≤8) / category / seller / url / specs`
- 前置：需企业资质在 `open.1688.com` 申请 ISV App Key/Secret + 用户 access_token（`alibaba.py` 只透传手工填的 token，无 OAuth 换 token）。

### 2.2 页面解析兜底（pds-tool `backend/app/sourcing/parser.py`）

- URL：`https://detail.1688.com/offer/{offer_id}.html`（`parser.py:19`）
- 请求头：仅 UA + Accept + Accept-Language（`parser.py:97-104`），无登录态——**符合我们「非登录采集」决策**
- 解析（`parser.py:25-29`，3 条正则 + 递归找值）：
  - `window.__INIT_DATA__\s*=\s*(\{.*?\});`
  - `window.runParams\s*=\s*(\{.*?\});`
  - `"offer"\s*:\s*(\{.*?\})\s*,\s*"supplier"`

```python
_DATA_PATTERNS = [
    re.compile(r"window\.__INIT_DATA__\s*=\s*(\{.*?\});", re.DOTALL),
    re.compile(r"window\.runParams\s*=\s*(\{.*?\});", re.DOTALL),
    re.compile(r"\"offer\"\s*:\s*(\{.*?\})\s*,\s*\"supplier\"", re.DOTALL),
]
```

- 关键字段路径：`subject/title/offerTitle`、`price/priceRanges/unitPrice`、`quantity/stock/canBookCount`、图片 (`imageUrls/images/picUrls/imageList`)、`categoryName/companyName`
- 图片兜底正则：`cbu01\.alicdn\.com…jpg|jpeg|png|webp`
- 链路（`service.py:43-92`）：`import_offer` 先试官方 API（`configured` 且成功后），`configured` 或 API 失败时再走 `parse_offer`（`alibaba_allow_parse_fallback` 开关，默认开）；都失败则落 `FAILED` 占位行。

```
import_offer(offer_text)
  → extract_offer_id()              # parser.py:164  offer/(\d+) 或 6+ 位数字
  → client.configured ?             # 有 AppKey/Secret 才试 API
       ├─ get_product_detail() ok → SOURCED
       └─ 异常 → ↓
  → parse_offer()（fallback 开时）  # httpx 详情页 → SOURCED
  → 都失败 → FAILED 占位行（error 记原因）
```

### 2.3 已知坑 / 待验证（务必先修再抄）

| # | 问题 | 位置 | 影响 | 处置 |
|---|------|------|------|------|
| 1 | `url` 变量在 `_parse_html` 里使用却未在函数内赋值（`url` 只在 `parse_offer` 定义） | `parser.py:158`（返回字典里的 `"url": url`） | 页面解析成功路径首跑即 `NameError` | 我们实现时把 `url` 作为参数传入或构造 `f"https://detail.1688.com/offer/{offer_id}.html"` |
| 2 | 搜索**无页面兜底**：`service.search` 未配置凭证直接返回空 + warning | `service.py:28-40` | 自动撒关键词搜索需官方 API 资质 | 若要关键词自动采集，需**自建搜索页解析**（反爬强）或走 API |
| 3 | 详情页反爬变化、搜索列表页反爬更强 | chunk 2.1/流程方案 §6.6 | 非登录采集受 IP 频率/UA 限制 | 低频调度 + 随机延迟 + 失败自动停 + 告警；兜底 CSV |
| 4 | 官方 API 无 OAuth、token 手工填、返回字段名多版本 | alibaba.py 全域 | 字段归一化靠 `or` 兜底，可能漏 | 抄时保留防御性 `or` 链 |

## 3. 转换（可直接移植：pds-tool `backend/app/transform/mapper.py`）

> 结论：标题去噪、加价、类目映射、描述生成都是模块级常量 + 纯函数，**整体照搬**到我们 `collectors/alibaba/transform.py`（现骨架只留了 clean_title 雏形）。

### 3.1 标题去噪（`mapper.py:21-25,44-54`）

去噪词表（最长优先替换）：`厂家直销/一手货源/微商爆款/地摊/批发价/源头工厂/代发/一件代发/现货/新品/热销/低价/特价/淘宝同款/天猫同款/拼多多同款/9.9/包邮`；再剥 `【】` `[]` 内容、压缩空白、`strip(" -|/【】[]")`。

### 3.2 加价（`mapper.py:66-71`）

```python
target = source_price * markup_ratio
return round(target, 0) - 0.1 if target > 10 else round(target, 2)
```

> `>10 元 → 整数 −0.1`（19.9 式尾数定价）；`≤10 → 保留 2 位`；默认倍率 1.3。

### 3.3 类目映射（`mapper.py:28-41,57-63`）

关键词规则表 `[(源关键词列表, 目标类目)]`，命中任一词即映射；未命中回源类目。例：手机壳/保护套/硅胶壳→手机配件/保护壳、数据线/充电线/Type-C→数码配件/数据线 …
> ⚠️ 这些是 PDD/抖音类目话术，**闲鱼类目不同**——我们上架走 `recommend_category`（MTop AI 类目推荐，publisher.py:132），此表仅作备用/预览，不强制使用。

### 3.4 描述生成（`mapper.py:107-123`）

HTML 拼接：加粗标题 → 规格参数 `<ul>`(≤20) → 货源 1688(seller) → 商品图片 `<img>` 列表；经 `sanitize_html` XSS 清理。

## 4. 定时铺货（调度模型，可直接照抄 pds-tool `backend/app/scheduler.py`）

### 4.1 设计（`scheduler.py:20-100`）

**`AsyncIOScheduler` + 常驻 `interval` scan job（60s）扫表**，不把每个任务注册成独立 job：

```python
_scheduler.add_job(_scan, "interval", seconds=60, id="pds_scan", max_instances=1)

# _scan（:33-62）：
# 1. 查 cron_expr!='' 且非 RUNNING 且 next_run_at 为空 or 已到期 的任务
# 2. next_run_at 为空 → 用 _next_run(cron_expr) 初始化
# 3. 到期 → 提前算好下一次 next_run_at → 写库 → asyncio.create_task(_safe_run(task.id)) 后台执行
```

- 下次运行时间计算（`scheduler.py:24-30`）用 **`CronTrigger.from_crontab(cron_expr).get_next_fire_time(...)`**（标准 5 段 `分 时 日 月 周`），失败返回 None。
- 立即执行只更新 `next_run_at`（`schedule_task_now`，:91-99），不额外建 job。
- 失败记录写 `TaskLog`（`_safe_run`，:65-71），调度器不依赖 `croniter`。

### 4.2 对照我们现状（`xianyu-core/backend/app/scheduler/task_runner.py`）

| 维度 | pds-tool | 我们现有 `task_runner` | 差距 |
|------|----------|----------------------|------|
| 扫描机制 | APScheduler interval 60s | asyncio 循环 60s tick | 等价，可保留我们方案 |
| 到期判定 | cron_expr → `get_next_fire_time` 算 `next_run_at` | 常量表 `TASK_INTERVALS`（600s 写死）+ DB 租约 | **我们要加 cron 支持**：任务表迁 cron_expr + next_run_at |
| 并发互斥 | `status != RUNNING` + 无租约 | DB lease（token/owner/expires）UPDATE 抢占 | 我们更稳（pro 同款），保留 |
| 任务种类 | 铺货任务 | order_sync / delivery_recovery | 需新增 `collect_1688` 与 `auto_publish` 两类 |

> 落地方案：**保留我们的 `TaskRunner` DB 租约**（防止多副本双跑），把到期判定从 `TASK_INTERVALS` 换成 `scheduled_task.next_run_at`（由 cron 表达式算），即 pds-tool 的 `_next_run` + 我们的 `_claim` 结合。这也是 pro `scheduled_task` 的做法。

## 6. 落地方案与验收

### 6.1 立项清单（按依赖排）

| # | 任务 | 关联参考 | 验收 |
|---|------|---------|------|
| 1 | `collectors/alibaba/parser.py` 补全：修 `url` bug、`parse_offer` 详情页抓取+解析、`SourcedProduct` 输出 | pds parser + 我们 `collectors/base.py` | 单测：喂假 HTML 提取出 title/price/images |
| 2 | `collectors/alibaba/aleriy.py`（可选）：官方 API 客户端（MD5 签名） | pds `alibaba.py` | 有凭证时请求构造/签名单测 |
| 3 | 关键词搜索自动入池：`search_98()` 批量 import（落 SOURCED） | pds `service.py` + 我们 CSV 管线 | 单测 + 低频调度 |
| 4 | 定时采集任务 `collect_1688`（scheduler）+ cron 表达式支持 | pds `scheduler.py` | 调度单测：到期触发 → 写 Product |
| 5 | 定时上架任务 `auto_publish`：池内 MAPPED→逐个 publish | 我们 `publisher.py` | 调度单测 + 手动小号实测发布 |
| 6 | 前端：1688 采集参数页（凭证/倍率/类目表）+ 任务配置页 | pds settings/tasks | 页面可存、可跑 |

> ⚠️ 阶段 5 闭环前，本地先以 **CSV 导入**跑通「入池→审核→定时上架」：换 `collect_1688` 为 `csv_import` 即可，发布链路先行实测。

### 6.2 数据流（并入现有 双品类 流程）

```
[定时] collect_1688  (间隔/Cron)
   ↓ httpx 详情页 / 官方API
SourcedProduct (offer_id/title/price/images/category/seller/specs)   # collectors/base.py
   ↓ clean_title + markup + map_category                            # collectors/alibaba/transform.py
Goods(category=B, pool_status=MAPPED, price_cent=按分)              # 复用 goods 表
   ↓ [人工/自动] 审核 → 入上架队列
[定时] auto_publish（cron / intervalMinutes 错峰）
   ↓ ItemPublisher 四步（传图→类目推荐→默认地址→publish）
external_goods_id 回填 + status=1 + pool_status=PUSHED + snapshot
```

### 6.3 风险清单（写入阶段 5 风控）

1. 1688 详情页/搜索页反爬变化 → parser 单测用**固定 fixture**，抓取失败自动停 + 告警；
2. 官方 API 无企业资质用不了 → 双路降级逻辑要稳（API 失败回页面解析）；
3. 闲鱼发布写操作风控最敏感 → 上架频控 1 次/分钟 + 随机延迟 + 小号试探；
4. pds 类目映射是针对 PDD/抖音的，闲鱼用 `recommend_category` 为主。
